Executive view

What this programme is

The Lufthansa Group airlines' Data Warehouse (the "Corona" Teradata estate) — serving all group carriers (LH, LX, OS, SN, 4Y, EN, VL, AZ, WK), not Lufthansa alone — is being re-platformed to the Databricks Lakehouse on Azure — Unity Catalog, Delta, serverless jobs, Databricks Asset Bundles — with a hard bar of 100% logic parity: every migrated stream must reconcile against Teradata (three consecutive 100% AVF runs) before it is signed off. Work is sliced into 11 communities (lineage-connected waves), executed by 9 squads (domain teams), and industrialised by a shared utility wheel and orchestration pattern so that every stream flies the same, repeatable route: extract → convert → post-process → deploy DDL → load → E2E run → AVF recon → sign-off .

Executive risk strip — what can move the date

Timely deployment

Community waves are sequential — a late DDL/data-load/pipeline readiness item in one wave pushes every wave behind it. The pre-prod runbook () exists to make readiness checkable, not hopeful.

scheduleOwner: Programme Lead

DQA & UAT sign-off throughput

Sign-off needs 3 consecutive 100% AVF runs plus DQA verification per stream — and the delays are mostly technical: edge-case defects surfacing late in validation, Teradata-side run failures invalidating comparison baselines, and the incident/defect tickets these raise, each of which must be closed before the gate.

technicalOwner: Pod Leads + DQA

Code unfreeze at Teradata end

Parity is only provable while the Teradata source is frozen. Any unfreeze on the legacy side invalidates recon baselines and can force re-conversion and re-validation of affected streams.

dependencyOwner: TD Platform Owner

Production planning

Cutover choreography — BIM data-load requests, schedule activation, parallel-run windows, rollback plans and ops handover — must be planned per community, not per stream.

cutoverOwner: Cutover Manager + RSA
Delivery standardThe bar is production-ready pipelines, not closed tickets: every stream must be optimised, resilient and cost-efficient — long-runners root-caused, legacy anti-patterns removed, and each optimisation proven at parity. Reusable fixes and hard-won lessons are captured in a shared knowledge base so a problem solved once isn't re-solved per squad — and so the playbook carries to the next migration.

How we de-risk running them together

Convert families once, deploy per waveConvert a whole family (all carriers) together even when members land in different communities — one review, one fix, no divergence between C2 and C5 inventory.
Producer-before-consumer across wavesSequence registry producers first (C2 inventory → C1 consumers); anything crossing communities becomes an explicit readiness gate in the E2E job, not an assumption.
Front-load data & prerequisitesRaise data requests and run the prerequisite pass ahead of the wave — data availability is the top blocker, and the year-end tail has no slack to absorb a late request.
Balance the RM bottleneckRM owns the most in-scope streams (50) and recurs across C5/C6/C4/C3/C7/C8 — level the load, pull RM-heavy conversion earlier, and add reviewers so RM isn't the single point of delay for the tail.
Protect the year-end clusterTreat C3+C7+C8 as one plan: pull conversion into Nov–Dec, complete UAT before the holiday freeze, and keep provisional freeze-end dates that flex on live defect status.
Systemic fixes clear batches at onceThe template fixes (SET-protection, timestamp precision, collation) resolve across every stream in a batch simultaneously — fix once, and the whole parallel wave benefits.
Stabilise before acceleratingClose urgent defects on the landed waves (10/9/5) before piling on new parallel waves — a shaky baseline makes every parallel comparison unreliable.

Plan by hard-stream count, not script count

Volume ≠ effort. C2 has 2,000 scripts but only 4% hard (bulk inventory + SAMBA); C1 has 906 scripts and 37% hard with 38 very-complex. The risk lives in C1, C7, C5, C8 (high % hard) — size the plan on the hard tail, not the raw counts.

Community 1 is the risk epicentre

Most complex wave in the plan: 38 very-complex streams, 44 Unix streams, plus the SBRRES/OSI families and the CUST_ID registry (55 consumers). Pre-prod 25 Aug — start its hardest streams first, staff senior reviewers, and don't expect to compress it.

IMP_SAMBA is a mini-project

A single stream carries 1,456 scripts (~23% of all in-scope scripts), PPL squad, Community 2 — already flagged as a date blocker. Give it its own runway and tracking; it gates C2, and C2 mints the registries C1 depends on, so a SAMBA slip cascades.

Unix is a front-loaded critical path

C0 (51) and C1 (44) carry the most Unix (.unx) streams — a distinct skill and step (Unix framework + prep team). Resource and sequence Unix conversion before those waves, or it becomes the bottleneck.

Heavy families concentrate effort

Beyond SAMBA: EXP_PARTNERS_* (C6, ~528 scripts across LG/LO/LHG/OS) and IMP_DCS_CDW_* (C7, ~205). Convert each as a family once — one review, one fix — rather than per member.

Operational load is daily-dominated

214 of the in-scope streams run daily (vs 45 monthly, 28 weekly). Cutover must follow the daily clock order, and day-2 monitoring/ops capacity must be sized for a mostly-daily estate — not a monthly one.

Architect's readThe estate is bimodal: a large, simple bulk (C2 inventory, C6 exports, C10) that converts fast, and a small, dense tail (C1's 38 very-complex, C7, the SAMBA monolith) that carries the schedule. Move the simple bulk early to bank progress, and put senior capacity on the dense tail from day one. The ~3,751 cross-community table-sync links mean the sequencing constraint is data dependency, not stream count — producer waves (C2 registries) must lead their consumers (C1), and dual-feed (Teradata + Databricks) covers the gap until the consumer wave lands.
PM's watch-list(1) Community 1 — highest complexity, can't compress. (2) IMP_SAMBA — single biggest item, gates C2→C1. (3) Year-end tail (C7 is 37% hard + C3 + C8) over the holidays with RM's 15–20-day test claim. (4) Capacity: RM spans the whole tail, PPL owns SAMBA + FFP — both are single points of delay. (5) Unix front-load for C0/C1. Mitigate each with earlier conversion starts, family co-conversion, front-loaded data, and levelled squad load.

Governing decisions — the ADR register & platform standards

Cross-cutting choices are settled centrally in Architecture Decision Records (ADRs), not per stream. The rule the whole programme follows: no ad-hoc fixes for a systemic problem — if an issue spans streams, it waits for (or triggers) an ADR, and every squad then implements it the same way. Each squad reads the ADRs that touch its code before its first PR.

Housekeeping, archival & GDPRADR-013Housekeeping logic is never removed blindly. When a wave starts, its housekeeping / archive / GDPR / statistics streams are identified and either migrated or folded into the target logic. Storage-lifecycle policy is owned by the platform side; stream-level housekeeping stays aligned to the ADR.

GCFR streams — what they are, and how we re-architected them

What GCFR isGCFR (Global Control Framework) is Teradata's generic, metadata-driven ETL control layer that the IDM streams run on. It provides the machinery around the SQL: a process/stream registry, business-date & cycle control (load-status tables), the step pattern (input view *_VI_* → transform → output view *_VO_* → materialized transform table in DB_TRANS_*), surrogate/BK key allocation, and the SCD2 apply into the shared DB_IDM targets. In short: a view-plus-apply, SCD2, surrogate-key framework — the logic lives in the views; GCFR decides when each step runs and where its output lands. 63 IDM streams in the final register run on it.

A large family of the IDM streams run on GCFR (the generic control framework). Anyone picking up a GCFR stream needs the whole picture below — what a stream is, what the old Teradata setup did, what broke on the naive Databricks port, and the revised design we ship. What a GCFR stream actually is

A stream is a chain of SQL steps. Each step reads some source tables, transforms the data, and writes the result somewhere. The steps run in order (050 → 070 → 100 → 200), and the final steps write into the shared target tables in DB_IDM (like OND_COMPOSITE_TIX, SEG_BKG_CLS).

In the GCFR control metadata each step is an input view (*_VI_*) → transform → output view (*_VO_*) writing a transform table in DB_TRANS_* before the final DB_IDM target — e.g. IDMRES_CORE_180_09_TX_TRAVEL_COUPON. What the old Teradata setup did

  • Each step was a view (the SQL logic). GCFR ran that view and saved its output into a real table, then the next step read that table — so every step was physically written down, even in Teradata.
  • All the streams ran together in one nightly batch, reading one shared copy of the source data. Because they all read the same data at the same time, their outputs were consistent.
  • Validation (AVF) checked the whole final result after everything finished.

What went wrong on the naive Databricks port

  1. Each stream copied the source itself, at its own time — every job runs a data_load that overwrites the DB_IDM tables from Teradata before it runs. Network at 09:12, Sales at 05:13 read two different versions of the same data → outputs stopped matching.
  2. Every step wrote a full table (INSERT OVERWRITE) — a lot of write/read to disk that Spark doesn't actually need.
  3. Streams ran separately and were validated separately, so the inconsistency between them was never caught or reconciled.
  4. Specific slow spots — e.g. a join that silently stopped using two of its three keys (mismatched text-column collation), blowing one step up to 8 hours.

What we changed — the revised approach

1 · Read the source once, together

Instead of each stream making its own copy of DB_IDM at a different time, all streams read one frozen snapshot taken at a single moment. Now every stream sees the same data, so their outputs line up again.

2 · Stop writing every step to a table

Turn intermediate steps into temporary views (CREATE TEMP VIEW) or CTEs inside one query. Only write a step to a real table if it's genuinely reused many times or needed as a restart point. Fewer writes = faster.

3 · Combine redundant passes

Where the old code scanned the same big table three times (two NOT EXISTS checks plus a MAX), do it in one GROUP BY … HAVING. Same result, one pass instead of three.

4 · Make the join keys actually match

The 8-hour join joined on three columns but used only one, because the text columns had different collation. Put the same COLLATE UNICODE_CI on both sides so the join uses all three keys and stops multiplying rows — hours → minutes.

5 · Reuse logic instead of copy-pasting

The same blocks (audit columns, "get the latest active row", insert/merge, compare) are copied into every step today. Put them in shared functions — one copy — which also removes copy-paste bugs (like the hard-coded timestamp in the Sales step).

6 · Validate the combined result, check every rewrite first

Point validation at the full target after all streams finish, matching the old batch behaviour. And before trusting any rewrite, run a small edge-case test — old SQL vs new SQL side by side — confirming they return exactly the same rows.

7 · Let Databricks tune itself

Remove the manual SET knobs (they were making it worse) and let the engine (AQE) handle partition sizing and skew.

The resultThe two OND streams stop disagreeing, because they read the same snapshot. The inventory step runs in a fraction of the time, with identical output (proven by the side-by-side test). The code is simpler — temp views + one pass instead of many table writes and repeated scans — and it works on serverless (no CACHE, no CREATE TABLE).
In one sentenceRead the source once so all streams agree, keep intermediate steps as views instead of writing them all down, do each thing in one pass, make join keys line up so nothing explodes, and prove every change gives the same answers before shipping.

The finalized conversion method — keep the logic, drop the materialization

Core idea: the trans/IDM layer becomes virtual — write only the targets. The literal port reproduced GCFR's spool-era pattern: every step INSERT OVERWRITE into its own db_trans_idm table (write→read round-trips Spark doesn't need). The revised design: every intermediate step is a TEMP VIEW / CTE; only the target tables (DB_IDM.OND_COMPOSITE_TIX, SEG_BKG_CLS, …) are physically written via MERGE/INSERT. An intermediate is materialized only when it earns it — reused many times, a recursion/lineage break, or a genuine restart checkpoint. Redundant passes collapse: where the old code scanned a big target 3–4× (multiple NOT EXISTS + a MAX), one GROUP BY … HAVING does it.

Worked example — INVENT_400_23 (the 8-hour step)

Intermediates → temp views; target reads 4× → 2×; the 30M-row double-derivation collapsed into one aggregation. Root cause found on the way: a collation mismatch had silently demoted a 3-key join to a date-only near-cartesian — matching COLLATE UNICODE_CI on both sides restored all 3 hash keys. Join fell from ~90% to 4.6% of plan time; 8 h → minutes, output byte-identical.

One-line summary: GCFR is a view-plus-apply, SCD2, surrogate-key framework; on Databricks we keep the transformation logic but make the trans/IDM layer virtual (temp views), write only the target tables, run serverless-clean with AQE, keep all streams on one snapshot, and allow concurrent writes through Delta row-level concurrency — proving every step byte-identical before it ships.

Delivery discipline — the standing expectations behind the flight plan

Stabilise before you accelerate

Urgent defects on already signed-off streams take priority over new development. A wave isn't "done" until its urgent defects are closed and its validation holds — closing beats starting.

Readiness before a new wave

Each new wave runs a prerequisite pass first: source / stream availability, ODAT validated, up- and down-stream dependency analysis, code + Unix conversion, DDL deployed, data loaded & reconciled — tracked on a readiness tracker, owned by pod leads, reviewed daily. Data requests are planned ahead of the wave, not raised mid-week.

Defects & incidents

One tracker, correct statuses, daily metrics with ageing and closure tracking. Every incident/defect on a stream is closed before its sign-off gate; recurring conversion gaps are fed back to improve the converter.

KT & documentation gate

Stream documentation is finished before KT; KT readiness is a prerequisite for squad hand-over. Streams near sign-off must have all supporting docs finalised and reviewed.

Operational ownership (day-2)

Beyond migration: documented restart procedures, a plan for signed-off-stream failures, operational runbooks and KT material, and trained platform-operations teams. A monitoring function owns RCA, incident management and defect closure, mapped to pod leads.

Reporting that says something

No "no progress" updates. Weekly reporting shows volume delivered, % complete, blockers, dependencies, environment & data-load issues, sign-off blockers, and technical risks with a closure plan.

Data & environment dependenciesThe most common delivery blockers are external: data-load requests, source-platform sync, file-format or export-folder changes, recon-table dependencies and missing pre-prod data. Surface these early and explicitly — they move dates more often than code does.

DevOps process — how code travels from a laptop to pre-prod

This tab explains, from scratch, how a code change travels safely from a developer's laptop to pre-production — the branching model, the local checks, the two automated gates, and the human reviews. Start with the plain-language Overview; the other sub-tabs hold the exact commands and rules. It's written so someone brand-new — or a team on a different migration who wants to copy this setup — can follow it end to end. (Governed by the Dev Squad Git Branching SOP and the Pre-Commit & PR Validation Guide.)

What this is — in one paragraph

Every code change (a converted SQL script, a job definition, a table DDL) has to get from a developer's laptop into the shared environments without breaking anything and without one person's mistake reaching everyone. The DevOps process is the set of rails that makes that safe: developers work on their own copy, automated tools check the code the moment it's written, an AI reviewer and a human lead both sign off, and only then does the change deploy — first to a Dev environment, later to a Pre-Prod (production-replica) environment. Nothing moves on trust; every step leaves evidence.

The journey in plain words

Follow one change from start to finish. Each step has a dedicated sub-tab above with the exact commands.

1
Pick up a task and make your own copy of the code. You never edit the shared code directly — you create a branch (a private copy) named for your task, taken from your team's branch, not the main one.
2
Set your laptop up once. A few free tools are installed that automatically check and tidy code (formatting, SQL rules, secret-scanning). This is the "workstation setup".
3
Write your change; the checks run as you save. Every time you commit, those tools run automatically and block the commit if something's wrong — so problems are caught in seconds, on your machine, not hours later.
4
Open a request to merge (a "PR"). When ready, you ask to merge your branch into your team's shared branch. This opens the change up for checking by machines and people.
5
Automated gate 1 — validation. A pipeline re-runs all the checks and enforces the rules (e.g. your change may only touch your team's files). If it fails, the PR can't proceed.
6
Automated gate 2 — the AI reviewer. An AI agent reads your change against the migration rules and the original Teradata code, and leaves comments — flagging anything from a risky pattern to lost logic. Serious findings block the merge.
7
Resolve everything — with proof. You address every comment (AI and human) and explain what you did and how you know it's right. "Done" or "N/A" with no explanation is reopened.
8
A human lead approves, and it deploys to Dev. Your team's lead reviews and approves; on merge, the change is automatically deployed to the Dev environment.
9
Promote toward Pre-Prod. When a batch is ready, it moves toward pre-production through a controlled merge; dev-only scaffolding is stripped automatically, an Ops reviewer checks it for alignment & performance, and it deploys to the Pre-Prod (production-replica) environment for validation and sign-off.

Why it's built this way

Catch problems earlyA bug caught on your laptop costs minutes; the same bug found in pre-prod costs days and can invalidate a whole validation baseline. Every gate exists to move the catch earlier.
Each team owns its own spaceTeams work on separate branches, so dozens of people can work in parallel with fewer collisions, and it's always clear who owns a change.
Consistent quality, whoever's workingTwo automated gates plus a human review mean the standard doesn't depend on who wrote or reviewed the code — the same rules apply every time.
An auditable trailEvery comment is closed with a reason and evidence, so six months later anyone can see why the code looks the way it does. That trail is what sign-off relies on.

Dev-environment jobs have been left running untracked for hours and, in several incidents, for days: a single long-running job can quietly burn a large amount of compute with no significant output, and others run 8–10 hours during testing/validation and produce no value. Nothing malicious — just missing defaults: no timeout, unbounded retries, nobody watching duration, and no cost attribution to a person.

Root causeEvery runaway shares the same anatomy: (1) no job/task timeout, (2) retry storms on non-transient errors, (3) no duration alert, (4) nobody could see whose job it was. All four are cheap to fix and are now mandated in the Guardrails pane.

Cost-ops design principles

1
Every job has a timeout — no exceptions.

A job without a timeout is an unbounded liability. Stream tasks already carry timeout_seconds: 3600; the same discipline applies to every dev notebook job. "No timeout, no merge."

2
Retries are bounded and justified.

Retry only what is provably transient (the utilities retry Delta concurrency conflicts with backoff — that's the model). Never blanket-retry OOM or logic errors: a retry storm is a cost multiplier on a bug.

3
Long-running is a decision, not an accident.

Any planned run >6 h needs Pod-Lead approval in advance — name, reason, expected duration and rough cost. Unplanned >6 h runs are killed by default.

4
Breaches page a human immediately.

Any test/validation job crossing 6 h triggers an immediate notification to the Architect and Pod Lead — not a morning-after report.

5
Cost is visible per developer.

Tags attribute every DBU to a squad and stream today — dev compute additionally carries the developer's identity so the weekly report has names, not mysteries.

6
Profile before you scale.

The default answer to "it's slow" is a query profile, not a bigger cluster. Most long-runners in this project were unoptimised patterns, not undersized compute (examples in Developer hygiene).

Code optimization — how we cut execution time (and cost)

Principle: fix the pattern, not the machine. Long-running jobs are usually lifted Teradata patterns, not a compute shortage. Bigger compute is the last resort, backed by a profile. Shorter runs = fewer DBU-hours and shorter cluster uptime, so these fixes are a direct cost lever the dashboards then confirm.

Diagnose first

  • Open the Query Profile (DBSQL) or Spark UI and answer three questions: longest stage? shuffle/spill bytes? is one task ~10× the median (skew)?
  • Fix the pattern the profile points at — never scale the cluster blind.

Case file 1 — the CORONA gap-pool mint (Teradata original)

In plain words: the old system dealt row numbers from a recycled deck of cards; the new one can't reshuffle that deck safely — so we switched to a simple ever-increasing counter.

The pattern behind CO_LEG_ID / CO_SEG_ID on the shared FLT registries. 96 genuine mint sites across 39 streams; mechanisms: 32 RANDOM+gap-pool, 53 row-number watermark, 9 pure RANDOM, 2 CSUM. Verbatim from inventory.120.TR_FLT_LEG.sql:

INSERT INTO <DB_ENV>DB_TRANS_INV.INV_CSI_RANDOM_NUMBER
VALUES (1,RANDOM(0,41))                                -- random bucket seed
...
SELECT ROW_NUMBER () OVER (ORDER BY COR.CORONA_ID) AS SEQ_NO, COR.CORONA_ID
FROM ( SELECT CORONA_ID
       FROM   <DB_ENV>DB_ODS.CORONA_ID_KEY_LIST               -- recycled-ID pool
       WHERE  CORONA_ID NOT IN ( SELECT CO_LEG_ID FROM <DB_ENV>DB_ODS.FLT_LEG )
       ...                                                    -- 9 more NOT IN guards
       AND    CORONA_ID MOD 42 = ( SELECT RANDOM_NUMBER FROM ...INV_CSI_RANDOM_NUMBER )
       AND    CORONA_ID < ( SELECT MAX(MAX_CO_LEG_ID) FROM ...TR_MAX_CO_LEG_ID )
       SAMPLE 10000000 ) AS COR

Deterministic values, non-deterministic selection — and Delta IDENTITY never reuses gaps, while the pool's lock-serialised selection has no safe concurrent equivalent. Migration answers: IDENTITY or watermark-continue with business sign-off; and note the NOT IN guards become a NULL hazard once constraints are stripped in Delta (family 3) — besides costing ten separate anti-joins.

Standing rule (ODS-IDENTITY freeze): any pre-mint "existing vs new" flag must be computed from a frozen table snapshot, not a lazy view over the registry being written — otherwise keys minted mid-run flip new rows to "existing" and attribute backfills are silently skipped.

In plain words: one setting makes 'AB' and 'ab' count as equal for business comparisons but distinct for key lookups — using the right one in each place keeps both correct.

Case file 4 — numeric parity (the IATA estimates fix)

In plain words: work out the ratio precisely, round it once, and reuse that same value everywhere — otherwise the cents drift.

Proration ratio must be computed in DOUBLE (Teradata FLOAT semantics), rounded once, then reused — note the alias reuse (PR referenced in the same SELECT): supported by Teradata's named-expression extension and by Databricks lateral column aliases (DBR 12.2+), so the round-once-reuse pattern converts 1:1:

SELECT CAST(CAST(SEG_DIST AS DOUBLE)/CAST(SUM(SEG_DIST) OVER(PARTITION BY REC_ID) AS DOUBLE)
            AS DECIMAL(18,4)) AS PR,
       TDAM_OND_EUR * PR AS TDAM_SEG_EUR,   -- lateral alias reuse: round once, reuse everywhere
       TDAM_OND_USD * PR AS TDAM_SEG_USD, ...

Where Teradata's half-even rounding matters, use bround() instead of round(); AVF's parity knobs (decimal_cast_precision=38, numeric_sum_overflow_safe) mirror the same rules on the validation side.

2 · What the Codex audit catches & fixes — the critical rules

The audit treats the Teradata source as the specification and compares logic, not formatting. It won't pass a file on a DML match alone — a mandatory control-boundary sweep runs on every file. The highest-impact checks, each with the fix it demands:

High Preserve source semantics — CAST is not TRY_CAST

SELECT TRY_CAST(amount AS DECIMAL(18,2))   -- draft: hides bad rows as NULL
SELECT CAST(amount AS DECIMAL(18,2))       -- fix: source used CAST — fail loud, identical in both engines

TRY_CAST changes behaviour by swallowing conversion errors. Allowed only when the source itself tolerates bad data or a change is explicitly approved.

Medium Subquery membership → EXISTS

WHERE id NOT IN (SELECT co_id FROM reg)      -- empties on a single NULL; correlated scan
WHERE NOT EXISTS (SELECT 1 FROM reg r WHERE r.co_id = t.id)   -- NULL-safe + anti-join

High Multi-table UPDATE…FROM → MERGE INTO

UPDATE tgt FROM src s SET tgt.rank = s.r WHERE tgt.id = s.id    -- not valid in Databricks
MERGE INTO tgt USING src s ON tgt.id = s.id
  WHEN MATCHED THEN UPDATE SET tgt.rank = s.r

Critical Preserve the transaction / fail-fast boundary — the audit's number-one rule

-- Teradata: grouped, fail-fast refresh
BEGIN TRANSACTION;
  DELETE tgt;
  INSERT INTO tgt SELECT … ;
  .IF ERRORCODE <> 0 THEN .QUIT 8;
END TRANSACTION;                              -- draft kept DELETE+INSERT but dropped the boundary → partial-write risk
BEGIN ATOMIC
  DELETE FROM tgt;
  INSERT INTO tgt SELECT … ;
END;                                          -- atomic unit restored: a mid-way failure rolls back, never half-loads the table

The mandatory control-boundary sweep flags a dropped transaction / fail-fast wrapper as High — Critical when a failed second write could leave a production table empty. A one-to-one DML match never clears this check.

High Rebuild machine-assembled table names

IDENTIFIER(CONCAT('db', :env, 'tbl', :table_suffix))   -- suffix mid-name / placeholder survived
IDENTIFIER(CONCAT('odp_adw_<squad>', :env_db, 'db_x.TBL', :table_suffix))
-- post-processor rebuilds the name and asserts no placeholder survives to deployment

High Align join types / collation (manual by design)

ON a.key = b.key         -- fails: STRING vs INT, or UNICODE_CI vs UTF8_BINARY mismatch
ON CAST(a.key AS STRING) = b.key           -- align types explicitly
-- or:  ON a.key = b.key COLLATE UNICODE_CI  -- align collation for Teradata-like matching

The converter transforms ETL without the converted DDL types in context, so it can't self-pick the cast/collation — the audit flags it and the developer resolves it.

High Nothing is silently dropped; every file carries a header

A multi-line statement still open at end-of-file, or a cell that isn't executable as written, always emits a finding — it is never counted as "covered". Every target file must also carry the standard header (Stream · Script · Author · Purpose · Version · Revision History); a missing header is High and is auto-filled from a template.

AVF table-sync timing — why correct code can still fail validation

Problem statementA converted stream can be 100% correct and still fail AVF. The reason isn't the logic — it's timing. A shared Teradata table is written by many streams at different times, and the three things that read it (Teradata's own writers, the data_load job, and the AVF metric collector) each touch it at a different moment, so they capture different versions of the same table. The current collector is also keyed on the Databricks run_id — a Databricks execution — not on a Teradata settled point, so it can't line up with what was actually loaded.
In plain wordsPicture a shared table as a whiteboard many teams write on all night. Teradata takes its photo after everyone has finished. Today Databricks either (1) photographs the board mid-writing — the photo is real but taken at the wrong moment (metric mismatch), or (2) tries to redraw the board itself — and if some teams haven't drawn yet, or draw in a different order, the redrawn board is genuinely different (data mismatch).

Two kinds of mismatch — tell them apart first

① Metric mismatch — a false alarm

The Databricks data may be perfectly correct, but AVF compared it against the wrong version of Teradata (read a moment too early/late). AVF FAILs, yet nothing is actually wrong.
Cause: the comparison happened at the wrong time.
Fix: fix when we read & compare.
Cost: wasted RCA time chasing phantom bugs.

② Data mismatch — a real defect

The Databricks output is genuinely different from Teradata — same logic, but a different version of a shared table was read, because it was produced/consumed at a different point in the sequence.
Cause: the produce→consume timing/order differs from Teradata, so the consumer reads an earlier or later version.
Fix: align the sequence — read the same version Teradata read.
Danger: it can be silent — AVF may even PASS while the version differs.

Below: Kind ① first (the timing race — why a correct table fails the compare), then Kind ② (why the data itself can be wrong if we produce instead of extract).

Kind ② · Actual data mismatch — reading a different version because the sequence differs

Data mismatch is not because Databricks computed something different — the logic is identical. It happens because Databricks produces and consumes a shared table at a different point in the sequence than Teradata did, so the consumer reads a different version of that table. A shared table has many versions through the night; the right answer depends on the consumer reading the same version Teradata's consumer read. When the produce→consume timing differs, the version differs — and so does the output.

Same table, same code — a different version is read because the sequence differs
Teradata
seq 3 write v1 ▸ seq 5 write v2 ▸ consumer reads v2 Databricks
seq 3 produce v1 ▸ consumer (seq 4) reads v1 — v2 not written yet
Same code, different versionTeradata's consumer used v2; the Databricks consumer used v1 — purely because the producer→consumer sequence timing differs. The rows aren't wrong, they're a different point in time, so the downstream output genuinely differs from Teradata. The example: Databricks produces at seq 3 and consumes at seq 4, but by Teradata's seq 4 the table had already advanced to its seq 5 version — so Teradata consumed a newer version than Databricks did.

The same root cause — a different version at consume time — shows up several ways:

Consumer runs too early — reads an earlier version

The producer hasn't yet reached the version Teradata's consumer read (a later writer hasn't run). Databricks consumes v1 where Teradata consumed v2 → fewer / older rows flow downstream. e.g. PARTY_ALIAS read before its late C4 writers (18:33–20:24) run.

Producer runs too far ahead — reads a later version

The reverse: Databricks has already advanced the table past the point Teradata's consumer read, so the consumer sees newer rows than Teradata did at the equivalent step.

Drift down a chain — versions fall out of step

Stream A builds table T; stream B reads T and builds U. If each runs at its own time, B may read a different version of T than Teradata's B did — and the gap widens at every hop. (The GCFR "read the source once, together" problem, in the output.)

Order-sensitive writes — the wrong version wins

When two writers update the same rows (last-writer-wins), a different run order makes a different version the "final" one at consume time — even though every individual write is correct.

Why this one is worseA metric mismatch is a false alarm — AVF FAILs, but the data may be fine. A data mismatch is real, and it can be silent: if the produced table and its downstream both read the same different-version state, AVF can even PASS while the output reflects a different version than Teradata — and it flows to UAT and beyond.
The safeguard we useTwo things keep the version aligned: (1) keep extracting shared tables from Teradata (full load) until the producer community has fully migrated — the extract is Teradata, so the version can't drift; (2) once produced in Databricks, replicate Teradata's produce→consume order with explicit dependency gates (the consumer waits for the right producer version) and pin the version read, so the consumer reads the same version Teradata's consumer read. Flip a table to "produced" only when all its writers are migrated and run behind a completion barrier with idempotent MERGE. Until then, produced content is a different-version risk by definition.

The issue flow — step by step where it breaks

1 · TD writes all day
7–18 streams (or 8 carriers 20 min apart) write one shared table across an 18–23h window — no single settled moment.
2 · data_load reads once
Copies the TD table at T_load → Databricks now holds one specific version.
3 · Collector reads again
The AVF collector reads TD live at T_collect (by run_id/schedule) → a different version.
4 · Versions diverge
A TD writer (or the next carrier) landed between step 2 and 3 → expected ≠ loaded.
5 · AVF mismatches
Compare fails on correct code; keyed on run_id, the metric can't even be re-aligned.
6 · Fan-out
Every downstream stream keyed on that table (40–52 of them) also fails → wave stalls.

Possible approaches — end to end

1 · Universal, event-driven collector

One collector, same logic on Teradata and Databricks, that fires the moment each job finishes (TD control-table signal / DBX on_success) — capturing that job's output at its settled point, not at an arbitrary clock time. This validates against the real TD output (also catching data_load errors), unlike reading the landed copy.

2 · Scope the metric to the job's own rows

Use the audit columns (process_name / update_process_name step, Decision 67) or the carrier code so VL's metric = VL's rows only. Then multi-writer / 20-min-cadence timing can't bleed one stream's data into another's compare.

3 · Key on cycle, not run_id

Store metrics in a metadata table keyed by (target_table, cycle_id, stream/carrier); AVF compares by lookup, asynchronously, off the run's critical path — no live TD hit, no double read. run_id stays for logging only.

4 · Version-pin & batch barrier

Read/compare the exact Delta version data_load wrote so later TD writes can't move the target; for whole-table metrics on PARTY/FACILITY/SEG_BKG_CLS, validate the settled state at the cycle boundary (e.g. after the 21:40 INT_IDM_INVENTORY consolidation) once all writers have run.

5 · Hybrid during migration

While a table's writers span migrated + not-yet-migrated communities, run the collector on the Teradata side and compare per-job contributions; switch to whole-table cycle validation only once the full writer set is on Databricks.

🗂 Deployment strategy & BIGINT

GUIDE Which DDL load mode — incremental, overwrite, or recreate?
  • Incremental — for minor DDL changes (add a column, widen a type). The default; least disruptive.
  • Overwrite — avoid; it can wipe/rewrite more than you intend.
  • Recreate — only when a structural change genuinely requires it, and knowing it drops+recreates the table.
Seen → fixedDDL errors traced to the wrong deployment mode. Fix: use incremental for small changes; reserve recreate for real structural changes.
GUIDE BIGINT widening — ALTER existing tables, CREATE-modify new ones

Widening an ID family (INT→BIGINT) touches many tables. The agreed strategy:

  • Already-deployed tables → apply ALTER statements (don't drop/recreate live data).
  • New tables → modify the CREATE DDL directly.
  • Keep DDL and ETL in separate feature branches / PRs; first identify which tables are already deployed vs new.
WhyALTER on live tables avoids data loss; the split branches keep the change reviewable and reversible. Run an impact analysis first — one widened key can ripple to far more tables than the obvious list.

🧪 Systemic checks (mismatch, code looks right)

CHECKLIST AVF mismatches even though the code looks correct

When execution succeeds but AVF won't reach 100%, walk this checklist before touching the SQL:

  • Source metadata differences — the two sides describe the data differently.
  • Deterministic IDs — surrogate keys generated differently from Teradata.
  • Row-number / ranking — ties broken differently (ordering or collation).
  • NULL handling — guards or joins behaving differently on empty values.
  • Filter columns — a predicate column changed meaning or type.
  • Pending source-side correction — the source itself is being fixed; parity can't hold until it is.
CASE Keys no longer align with Teradata (deterministic-ID mismatch)

AVF mismatches because generated IDs don't match Teradata — typically a Teradata-side row_number edge case or a key-generation discrepancy. Confirm whether the difference originates upstream before changing your code.

Project decisionIf the root cause is a source-side fix, classify it as a source-side issue — it then gates go-live under the deployment-blocked rule ().
GUIDE A source column changed behaviour — run the impact analysis

When a source column's behaviour changes (e.g. an operational sequence column), trace it everywhere before assuming it's harmless — one column can ripple into 8–9 downstream inventory streams.

  • Is it used in filters?
  • Is it inside a window / row_number?
  • Does it feed key / deterministic-ID generation?
  • Which downstream streams read the table it lands in?
RULE Every change must prove Old == New before it's accepted

Conversion compiling and running is not acceptance. Any optimisation or change must be proven equal to the previous result through row counts, column hashes and output parity — proven, not assumed. This is the standard AVF enforces, and it's why "it runs" is never enough to sign off.

🛠 Patterns & fixes

CASE A long INSERT OVERWRITE runs 6h+ and fails — even after adding memory

An INSERT OVERWRITE over a large (tens-of-millions-row) view runs for hours and fails repeatedly; bumping cluster memory (e.g. 16→32 GB) doesn't help.

Seen → fixedAdding memory rarely fixes a pattern problem. Do this: open the Query Profile and find the real cost — skew on a hot key, a shuffle-heavy join, or repeated scans of the same view. Bigger compute is the last resort, backed by a profile.
CASE A stream that was fine is suddenly slow after a data refresh

A query that used to finish now runs 2+ hours or hits the serverless timeout after a new data request. Usual causes: data-volume increase, partition skew, statistics differences, or a missing runtime optimisation.

  • Compare previous vs current row counts for the inputs.
  • Read the execution plan / Query Profile — look for a new skew or a switched join strategy.
  • Test on serverless and a job cluster separately to isolate a runtime difference.
GUIDE "Lift-and-shift" code runs slow on Databricks

Long-running jobs are often legacy Teradata patterns copied straight across. The expectation is a Databricks-native redesign, not a literal port: repartition, refactor the query, remove forced disk writes between steps, and optimise for the runtime. Slow lifted code is treated as a defect to fix, not a given.

GUIDE Does Databricks support recursive CTEs?

Yes on current runtimes — recursive WITH is supported (needed for the chain-building logic seen in GCFR and inventory streams). Rewrite Teradata recursive views as a standard recursive CTE with a renamed self-reference; if a runtime caps loop depth or rows, raise the caps deliberately or rebuild the loop as a window calculation.

GUIDE What good optimization actually buys you

Pattern fixes routinely turn hours into minutes — the wins are large because the problem is usually the pattern, not the compute.

Seen → fixedReal examples from revised code: one step dropped from ~1h 10m to ~2m, another from ~2h to ~1s. But watch for regressions — a different step got slower (9m → 46m) and had to be reviewed. Lesson: always re-profile the whole stream after an optimization; a fix in one step can shift cost into another. Prove Old == New on results while you're at it.

Architecture Review — the design decisions & concerns behind the build

The recurring architecture and design discussions from the community-migration and architecture forums, de-identified and distilled to the concern and the agreed direction. These are the "why it's built this way" companion to the how-to tabs — every row links to the tab that carries the detail. Type in the filter to find a topic fast.

The recurring principles

1 · Syntax ≠ semantics

Never migrate syntax-only. Preserve business meaning — NULL behaviour, type coercion, ordering — and validate the data, not just that it compiles.

2 · Prefer Databricks-native

Choose safer native features over legacy TD patterns: IDENTITY over MAX+ROW_NUMBER, catalog-managed Delta, BEGIN ATOMIC, AQE.

3 · Concurrency & uniqueness

Shared-key frameworks need real uniqueness and concurrency guarantees — parallel streams must not mint overlapping keys.

4 · Determinism

Wherever ROW_NUMBER or ordering logic exists, the ordering keys must uniquely define the order — or platforms diverge on identical data.

5 · Consistent architecture standards

Layering, naming and view/table separation stay consistent through migration — physical implementation reflects logical intent.

6 · Validate beyond tables

Validation architecture extends to exported files and end-to-end workflows, with results persisted so AVF can display them.

7 · Model implicit behaviour explicitly

Trimming, type conversion, NULL handling, timestamps and collation — TD's implicit behaviours must be modelled explicitly on Databricks.

New design — the Centralized (Universal) Metric Collector

Problem. Metric collection lives inside each stream's pipeline: a 2–3 min gap between the data-status check and the metric task lets other jobs write to the source first (false mismatches later), and a skipped/failed Databricks stream leaves no source metrics even though Teradata loaded.

Design (v2, consolidated). One central, continuous job per environment watches each stream's Teradata completion signal and collects as soon as the stream finishes there — independent of Databricks. It collects only; AVF validation stays a separate job reading avf_source_metrics (schema unchanged).

The decisive fix — pin the period

Shrinking the gap can't fix the race; collecting only the just-finished period (WHERE FILE_DT = DATE '{period}') does. A finished period is immutable, so timing stops mattering — and Teradata scans one partition, not the table.

core idea

Pluggable completion detector

status_table (simple status == completed_value) or cascade — the rich vx_cascade readiness model (restart-recovery, clean-stop/cycle-check, file-export gate, settle-time). A flat status='FIN' misfires on restarts; cascade doesn't.

per stream

VOLATILE guard

Un-pinnable full-refresh tables read a marker column before/after collection — if it moved, the snapshot is marked VOLATILE rather than pretended clean. Validation policy for VOLATILE (skip / warn / wider tolerance) is an open item.

2 · Conversion-rule additions (platform-difference findings)

#Rule
B1VARCHAR(n) overflow: Teradata silently right-truncates; Databricks errors on Delta write. Parity fix = explicit substring(col,1,n) at ETL write (centralized in the wheel). Never charVarcharAsString=true on the write path — storing the overlong string is itself a parity break.
B2VARCHAR(n) on external Parquet breaks the PySpark DataFrame read path (SQL works) → AVF can't validate those tables. Fix: charVarcharAsString=true in the AVF read session (safe) or route AVF reads via spark.sql(); DDL policy = STRING on external-Parquet tables.
B3Timestamp-literal / session-TZ hazard: TO_TIMESTAMP(:start_ts) in MERGEs is session-timezone-dependent → shifted end_ts writes (the origin of the +2h sentinel). Fix: CAST(:start_ts AS TIMESTAMP_NTZ) + pin session TZ; standardize sentinel literals to TIMESTAMP_NTZ.
B4A <=> B ≡ ((A=B) OR (A IS NULL AND B IS NULL)) and enables equi-join planning — the standard rewrite for wide change-detection anti-joins (turned a 10-min BroadcastNestedLoopJoin into a hash LeftAnti on 355 FLT_SEG_CLASS_HIST; verified 14/14 harness + 4,000-scenario fuzz).
