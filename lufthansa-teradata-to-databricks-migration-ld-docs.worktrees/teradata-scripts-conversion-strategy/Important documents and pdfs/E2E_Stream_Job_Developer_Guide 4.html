The E2E Stream Job — end to end, in plain language

Every stream you deliver is really two jobs. The stream job is your code — the converted scripts. The E2E job is the wrapper around it: it checks the source is ready, loads the data, runs your code, then proves the result matches Teradata. This guide explains the whole flow step by step in plain words: every task, every parameter, how one YAML file works in all three environments — plus flash cards and a "when you're stuck" table. The example throughout is IMP_TDA_BOOKING_GERMANY, but it's just an example — §9 shows the stream types that look different.

1 · The big picture — why an E2E job exists at all

Your code can transform data — but on its own it doesn't know the answers to five questions: Is today's source data ready? Is this the very first run here, or a normal daily run? Do my tables exist yet? Did the data arrive correctly? Does my result match Teradata's?

The E2E job answers all of that around your code. Think of it as an airport departure sequence: check the inbound aircraft has landed (Teradata done), decide if this is a new route's first flight (first load), make sure the gate exists (tables), board the passengers (data load), fly (stream run), and confirm everyone arrived (AVF). Your notebooks only ever fly the plane — the E2E does everything else.

Key insightThe order isn't red tape — each step hands the next one something it needs: the status check says "source is ready" → load_status says "first run or daily run" → that decides which setup runs → the load brings the data → your stream transforms it → AVF checks both ends match. Change the order and you end up checking data that was never loaded, or loading data Teradata hadn't finished writing.

Cycle check, explained with a washing machine A simple status check is glancing at the machine's "done" light. The cycle check is what an experienced person does instead: is that light for my wash and not the previous load? (→ pin tonight's cycle id, don't accept yesterday's FIN) · has the drum actually stopped? (→ reached FINISH properly, not merely "not running") · did someone restart it mid-cycle? (→ wait for the restarted run to really complete) · give it a minute before opening the door (→ settle time; and for file-producing streams, the export gate: the output file exists). Same question — "is it done?" — asked by someone who's been burned before. It's always per-stream, never per-family: sources finish at different times of night, so one shared check at the top would either wait on everyone or wave streams through too early.

4 · First load vs incremental load — one switch, two different runs

First load once per environment

The stream has never successfully loaded here. The environment may be missing tables, and there is no previous data to compare deltas against. So the E2E:

  • verifies/creates tables (Table_exists → ddl_deployment_recon)
  • loads the full snapshot
  • skips the metrics collector (there is no meaningful "before" picture; AVF still validates with load_type=first_load semantics — full-table comparison)

Happens again when you promote: first run in _i, first run in _p — "first" is per environment, not per stream forever.

Incremental load every scheduled run

Tables exist, yesterday's data is in. The E2E:

  • skips DDL work entirely (nothing structural changes daily)
  • photographs source metrics first (the timing-sensitive step)
  • loads only what the run needs (delta / overwrite per execution_mode)
  • AVF compares the just-finished period

This is the steady state — the run your stream lives in for years.

Key insightload_type is computed, never passed by hand. You don't tell the job "this is a first load" — load_status figures it out from control state. That's what makes reruns safe: run the same E2E twice and it re-derives the truth each time.

5 · ODAT vs ODAT_Incremental — the map and the day's route

ODAT is the master map. It says which Teradata table becomes which Databricks table, which tables a stream owns vs only reads, and which script touches what. Every framework reads this same map: DDL deployment to know what to create, data load to know what to copy, table-exists to know what to check.

ODAT (full)

The complete object map for the estate/community — every table a stream owns or reads. Used on first load: build and load everything the stream needs from zero. Versioned files (odat_file_name parameter — e.g. ODAT202608101824) so a run is reproducible against a known map version.

ODAT_Incremental

The daily subset — only the objects that participate in a recurring run (transform-owned registries that are seeded once, static reference tables and one-time loads are excluded from the recurring path). Used on incremental runs so the daily load doesn't wastefully re-copy (or worse, TRUNCATE-reload) tables that must persist — the exact lesson behind reclassifying CUSTOMER_ALIAS/FLT_SEGMENT as seed-once registries.

Classic trapFull-vs-incremental ODAT version mismatch reads as "dozens of missing tables" during validation. If table-exists or the load suddenly reports many missing objects, check which ODAT file name the run used before assuming a deployment gap.

7 · Stream job facts — the anatomy of your job

Structure

  • One task per converted script, named after it (bkgde_01_prepare_data ← bkgde.01.PREPARE_DATA.py), chained with depends_on in script-number order — the same order the ksh ran them in Teradata.
  • Notebooks referenced relatively (../src/…) so the bundle is self-contained.
  • Each task gets base_parameters like stream_base_dir (where this stream's files land under the volume, e.g. …/tda) and table_suffix.
  • Internal gates: a script can publish task values and a condition_task reads them — here exit_110 stops the run cleanly when bkgde_01 sets stop_stream=true (e.g. no file arrived). A clean planned stop, not a failure.

Runtime facts

  • Wheel environment: tasks run with odp_adw_utilities-…-py3-none-any.whl from the environment Volume — the unix_framework functions your scripts import.
  • Timeouts: per-task and job-level (3600s here) — no silent all-night hangs.
  • Schedule is PAUSED on the stream job — the E2E owns the schedule (05:00 Europe/Berlin, Mondays here); the stream is only ever triggered by the E2E's Stream_run. Never unpause the stream's own schedule.
  • run_as a service principal, not you — runs behave identically whoever deploys.
  • Queueing on (queue.enabled) + effectively single concurrent run — a late previous run queues the next rather than colliding.
  • Cost tags (odp_workload_*) on every job — how the cost dashboards attribute spend.

8 · Target variables — one YAML, three environments

You write the E2E YAML once. Nothing in it names dev, int or prod. Instead it uses ${var.…} placeholders, and the bundle's target files supply per-environment values at deploy time:

databricks.yml            ← declares the bundle + variables
resources/
  E2E_<STREAM>_RUN.yml    ← the E2E job (this guide)
  <STREAM>.yml            ← your stream job
src/                      ← the converted scripts
targets/
  target_dev.yml          ← env_id="_n", dev job-ids, dev service principal…
  target_int.yml          ← env_id="_i", …
  target_prod.yml         ← env_id="_p", …

Key insightThe only difference between dev, int and prod is which target you deploy with: databricks bundle deploy -t dev vs -t prod. If you catch yourself editing the YAML "for prod" — stop. That change belongs in the target file, not the YAML.

11 · Flash cards — the 60-second recap (click to flip)

What are the two jobs every stream ships as?
The stream job (your converted notebooks — the ETL) and the E2E job (the wrapper: source check → load decision → DDL/metrics branch → data load → stream → AVF).
Why does teradata_status run first?
Everything downstream copies or measures Teradata data — so first prove the source finished writing. Load a half-written source and AVF fails for a fake reason.
What is a cycle check and who needs it?
GCFR streams run in cycles (one cycle = one nightly batch). The cycle check confirms four things before copying data: it's tonight's cycle (not yesterday's FIN), it truly finished (not stopped or mid-restart), its output file landed (if it makes one), and it's been quiet for a few minutes. A flat status='FIN' can pass on all four lies; the cycle check can't.
What does load_status produce?
One task value: load_type = first_load or incremental_load — computed from control state + the data_load_time anchor. Every later task reads it. You never set it by hand.
What runs ONLY on first load?
Table_exists_job (verify every ODAT table exists) then ddl_deployment_recon (create what's missing). First load = nothing exists yet; on daily runs DDL never changes, so both are skipped.
What runs ONLY on incremental?
AVF_Metrics_Collector — photographs Teradata's metrics before the load, so validation later compares against the true "before" picture instead of a source that kept moving.
Why is the metric collector's timing sacred?
It must snapshot the source right after Teradata finishes and before anything else writes. Collect later and you get false mismatches. (The centralized collector solves this permanently by pinning the finished period.)
First load vs incremental in one line?
First load = build the world (tables + full snapshot, once per environment). Incremental = the steady daily state (photo → delta load → run → validate).
ODAT vs ODAT_Incremental?
ODAT = the complete object map (first load builds/loads everything). ODAT_Incremental = the daily subset — seed-once registries and static tables excluded so recurring runs never wipe what must persist.
What format is data_load_time?
YYYYMMDDHHMMSSmmm — e.g. 20260526201639731 = 26 May 2026 20:16:39.731. It anchors what "this run's data" means, makes reruns idempotent, and is your first breadcrumb in load investigations.
How does one YAML serve dev, int and prod?
Nothing in the YAML names an environment — every env-specific thing is a ${var.…} filled by targets/target_dev|int|prod.yml at bundle deploy -t <target>. env_id (_n/_i/_p) suffixes every catalog.
How does the E2E find the framework jobs?
By id, via target variables (${var.data_load_job_id} …). The frameworks deploy once per environment; each target file knows that environment's ids.
Why is the stream job's own schedule PAUSED?
The E2E owns the schedule; the stream is only triggered by Stream_run. Unpausing it would run your ETL without the source check, load, or validation around it.
What does AT_LEAST_ONE_SUCCESS mean on data_load?
data_load depends on both branch arms (Table_exists on the first-load side, the condition's false edge otherwise) — it proceeds when whichever branch actually ran succeeded.
What is stop_stream / the exit gate?
A stream-internal condition: an early script publishes stop_stream=true (e.g. no file today) and a condition task ends the run cleanly — a planned stop, not a failure.
How does AVF match source and target metrics?
By stream + period/version — never run_id. That's why the collector and validator don't need to share a run, and why the target side must be filtered to the same period.
When is a stream "done"?
3 consecutive 100% AVF runs + DQA verification — production-ready pipelines, not closed tickets.
AVF red but stream green — first suspects?
The silent-defect classes: collation, trailing spaces, rounding, timezone, non-deterministic dedup — then collector timing (stale source photo). Check which metric and table diverged before touching code.
